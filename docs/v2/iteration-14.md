# Итерация 14 — первый контракт QUIK

Дата: 13 октября 2026 года. Начало этапа 7.

Реализован проверяемый контракт SPBFUT и `QuikReplayGateway`, который подаёт события формата QUIK в существующие OMS/ledger. Шлюз записывает подготовленные транзакции в память и не открывает сеть. Это тестовый адаптер протокола, а не готовый доступ к реальному счёту.

## Выбор bridge и проверенные источники

В прежнем `core/quik_gateway.py` используется `quik-python`. Изучен исходный [Alex-Shur/quik_python, commit 0eae024ea43547ab933c705d0951d37e3533d675](https://github.com/Alex-Shur/quik_python/tree/0eae024ea43547ab933c705d0951d37e3533d675); его `pyproject.toml` указывает 1.2.0. ## Формат и идентичность

`QuikRoute(route, price_step: Decimal, commission_fields: tuple[str, ...])` явно задаёт точный счёт/инструмент, шаг цены и выбранные компоненты комиссии. Первый срез ограничен RUB-фьючерсами SPBFUT с целыми лотами. Метаданные инструмента и множитель должны быть проверены по брокерскому справочнику перед живой интеграцией.

`limit_transaction` строит структурированную таблицу NEW_ORDER: точные CLASSCODE/SECCODE/ACCOUNT, направление B/S, TYPE=L, целые QUANTITY и TRANS_ID, десятичная PRICE без экспоненты. Рыночные заявки, другой маршрут, дробные лоты и цена вне шага отклоняются до записи транзакции. Ключ отмены ORDER_KEY передаётся строкой. Клиентский код/поручение пока не формируется автоматически и должен быть согласован с брокером перед live.

Целочисленные номера читаются как int либо цифровые строки; float и bool для ID запрещены. Тесты используют номера больше 2^53. Диапазон локальных TRANS_ID намеренно ограничен 1…2^31−1: счётчик не закольцовывается. Это выбранное ограничение приложения. Префикс `session_id` входит в execution_id и должен сохраняться при повторной обработке одной брокерской сессии.

OnTrade требует точного маршрута, количества, направления, цены и времени. UTC offset терминала задаётся явно; микросекунды сохраняются, противоречие ms/mcs отклоняется. Нельзя подменять время сделки текущими часами. Комиссия складывается только из настроенных полей; отсутствующее поле — ошибка. Пустой список компонентов явно означает нулевую комиссию и допустим лишь когда это осознанно соответствует источнику. Итоговая схема комиссий брокера ещё должна быть проверена, чтобы не сложить уже включённые друг в друга сборы.

## Последовательность событий

| Вход | Результат |
| --- | --- |
| Ответ отправки `data=true`, OnTransReply 0/1 | Позиция и статус регистрации не меняются. |
| OnTransReply 3 для NEW_ORDER с номером либо проверенный OnOrder | Связываются локальный ID, TRANS_ID и номер брокера; публикуется GatewayAccepted. |
| OnTrade до появления соответствия | Сохраняется в ограниченном буфере. Если возможного своего незарегистрированного входа нет, блокировка немедленная. После установления точного соответствия применяется один раз. |
| OnTrade известной заявки | Единственный источник Execution и финансового изменения; одинаковый повтор не применяется, конфликтующий блокирует дальнейшую работу. |
| Запрос отмены до номера брокера | Ждёт регистрации, не отправляет KILL_ORDER с вымышленным ключом. |
| OnTransReply 3 для KILL_ORDER | Ожидание окончательного состояния заявки продолжается. |
| Терминальный OnOrder при нашей отмене | GatewayCancelled содержит `qty − balance`; OMS ждёт недоставленные fills, затем разрешает замену только остатка. |
| Полный OnOrder без OnTrade | Сделка не придумывается. Ожидаются исполнения; по таймауту блокировка. |
| Статусы 2/4/5/6/10/11/13 | Подтверждённый отказ входа либо отказ конкретной отмены; противоречие уже зарегистрированной заявке не затирает состояние. |
| Статус 12, неизвестный статус, неоднозначный ответ транспорта | Неопределённый исход, блокировка и сверка; автоматической повторной отправки нет. |
| Неизвестная внешняя заявка | Отдельный список unmatched и блокировка до inventory reconciliation; владельца стратегии не угадываем. |

Просроченные активные снимки не воскрешают терминальную заявку. Соответствие номера сохраняется после отмены, чтобы принять и дедуплицировать поздние исполнения. События известного исполнения обрабатываются и после блокировки связи; новые транзакции заблокированный replay-шлюз не записывает. OnConnected сам по себе блокировку не снимает.

`check_deadlines()` использует часы OMS. По умолчанию 90 секунд от запроса регистрации/отмены либо начала ожидания недостающих fills/соответствия. Повторные промежуточные события не продлевают срок бесконечно. Буфер неизвестных событий ограничен, по умолчанию 1000. При переполнении новый callback отклоняется с блокировкой; будущий live-вход обязан сначала сохранять исходные события для повторной обработки.

## Неопределённый исход в ядре

Добавлен `GatewayUncertain(gateway_id, reason)` в закрытый codec и журнал OMS. Он сохраняет необходимость сверки шлюза и нового капитала; не превращает заявку в REJECTED и не освобождает резерв. Неизвестный шлюз отклоняется. При восстановлении теперь сохраняются и блокировки шлюзов без заявок: их нельзя потерять при пересборке списка по ордерам.

Причина хранится в журнале, replay-шлюз предоставляет incidents. Это финансовая блокировка ready, а не новый lifecycle-статус стратегии. Полный процесс оповещения и повторного подключения относится к последующей интеграции. Обычные принятые финансовые события остаются доступны для учёта.

## Проверки и воспроизведение

Добавлено 27 тестов; первые 14 сценариев записаны до реализации. Тест восстановления блокировки без заявок сначала воспроизвёл потерю состояния, затем проверил исправление. Всего **391 тест**, strict mypy — **42 файла**, **14 примеров**.

`python examples/v2_quik_contract.py` читает `examples/fixtures/quik_order_flow.json`. Это синтетические данные по изученной схеме, не запись реального счёта. Ранний trade, отмена с late fill, замена двух лотов по 99, выход по 105 и повтор старого trade дают 18 RUB после четырёх комиссий. Следующая заявка без ответа остаётся SUBMITTED с резервом 150 RUB после 90 секунд. Перезапуск восстанавливает финансовое состояние и запрет новых действий без повторной отправки.

## Следующий срез этапа 7

До подключения живого транспорта нужны durable-выделение TRANS_ID и хранение соответствий до отправки, журнал исходных callbacks, обработка разрыва/переполнения очереди и независимая сверка заявок, сделок и позиций. В replay-шлюзе соответствия только в памяти; восстановление примера проверяет OMS, не восстановление сетевой сессии. Нельзя использовать его как live-adapter, просто добавив вызов send_transaction.

Затем подключаются read-only данные/счета и scheduler; после контрактной и демонстрационной проверки — реальное исполнение и нативная защита. Инструкция подготовки: [QUIK и Windows](quik-environment.md). Общий portfolio flatten, GUI и итоговая приёмка остаются незавершёнными требованиями прежнего плана.
