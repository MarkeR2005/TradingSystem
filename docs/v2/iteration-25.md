# Итерация 25 — принятие внешнего учёта и восстановление двух журналов

22 октября 2026 года. Ветка `rewrite/v2-quik-inventory-adoption` от `rewrite/v2-quik-inventory-plan`. Этап 7 продолжается; реестр сохраняет 32 use-case.

## Что добавлено

Сохранённый план из итерации 24 теперь можно принять в отдельном офлайн-контуре. OMS вводит внешние остатки с объявленной стоимостью и ручным владельцем, а шлюз сохраняет связи брокерских заявок и сделок. Команда `AdoptExternalInventory` связывает эти действия одним ID и точным содержимым. Повтор завершает прерванную операцию, не импортируя остаток второй раз.

Это первый ввод внешнего состояния для данного шлюза. Он не подтверждает атомарность брокерского снимка и не разрешает торговлю. Граница времени и стоимость остаются явными данными оператора; транспортный курсор не превращается в брокерское доказательство. Повторный ввод новой партии внешних остатков после принятой границы и исправления неизвестной старой истории требуют отдельного протокола.

## Порядок записи

1. После опустошения очереди захватываются блокировки шлюза и OMS. Проверяются здоровые журналы, текущая revision, сохранённый план, его свежесть и повторное построение по текущему наблюдению. Контракты маршрутов, комиссий и часового смещения сравнения и callbacks должны совпадать.
2. Изолированная копия протокола проверяет будущие связи и накопленные callbacks. Противоречивая история, чужой остаток буфера, неподдерживаемая заявка или коллизия останавливают операцию до финансовой записи.
3. OMS записывает решение и принимает финансовую базу. Полная сверка остаётся незавершённой; активная защита, планы и аварийное сокращение не допускают такой импорт.
4. Шлюз записывает отдельный input/result, устанавливает связи и базу дедупликации, затем доставляет только новые исполнения после принятой границы.

Это последовательное завершение двух журналов, а не общая транзакция файловой системы. Между шагами 3 и 4 возможен сохранённый финансовый результат без связей шлюза. Система остаётся заблокированной; restart и точный повтор завершают связи по уже записанному решению. Зафиксированное решение не отменяется задним числом из-за истечения срока снимка.

Команда содержит число записей и SHA-256 точного префикса журнала шлюза. На повторе этот префикс должен сохраниться, хотя после него могут появиться записи restart и новых callbacks. Одного совпадения имени сессии недостаточно. Digest проверяет соответствие локальной истории, не является подписью брокера.

При восстановлении шлюза с уже принятым учётом обязателен `recover(runtime.orders)`. До повторной доставки финансовых сообщений проверяется наличие тех же решений в восстановленном OMS. Старые журналы без принятия внешнего учёта сохраняют прежний способ вызова `recover()`.

## Финансовая семантика

| Данные | Результат |
| --- | --- |
| Внешний остаток | Вводится в `manual` с собственной объявленной средней стоимостью |
| Исторические исполнения импортированной заявки | Сохраняются как база дедупликации и история заявки; повторно не меняют ledger/P&L |
| Историческая комиссия | Остаётся в истории заявки, не списывается с новой финансовой базы второй раз |
| Новая сделка после границы | Обычный учёт исполнения, позиции и её собственной комиссии |
| Известный дубль | Не создаёт нового финансового результата |
| Неизвестная сделка до границы или точно на ней | Блокируется в протоколе шлюза до доставки в OMS; сырой вход и ошибка остаются в журнале |

Отсечение старых неизвестных сделок устанавливается и на ранее известные заявки шлюза, как в OMS. Конфликтующие дубликаты также требуют разбора. При такой ошибке финансовое состояние не меняется; replay восстанавливает зафиксированную ошибку, не пытаясь повторно провести недопустимое исполнение.

Накопленные исторические callbacks должны точно совпасть с объявленной базой. Накопленное новое исполнение после границы может быть доставлено при завершении связей. Уже связанная внешняя заявка сопоставляется по брокерскому номеру: её чужой `trans_id` не должен переназначить внутреннюю заявку с таким же номером транзакции. Импорт сам не выделяет транзакционные ID и ничего не отправляет.

Позиции существующих стратегий сохраняют владельцев и финансовую историю. Вызов не создаёт фиктивного рыночного исполнения, не запускает планы и не завершает сверку. Обычный `GatewayReconciled`, свежая политика капитала и прежний `InventoryReport` не снимают оставшуюся блокировку. Закрытие/передача импортированных позиций через торговый контур потребуют последующего допуска.

## API и восстановление

```python
# Сначала построить и сохранить review из итерации 24.
command = gateway.inventory_adoption_command("adopt-01", runtime.orders, review.operation_id)
await gateway.adopt_external_inventory(command, runtime.orders, raw_snapshot, policy)
await runtime.drain()
assert not runtime.orders.ready
```

После сбоя восстановить OMS из его журнала и открыть прежний журнал шлюза с тем же профилем:

```python
runtime.add_gateway(gateway)
await gateway.recover(runtime.orders)
await runtime.drain()
command = runtime.orders.external_inventory_adoption("adopt-01")
await gateway.adopt_external_inventory(command, runtime.orders, raw_snapshot, policy)
await runtime.drain()
```

Если решение ещё не попало в журнал OMS, это новая попытка: нужны актуальный план и действующий срок. Если решение сохранено, повтор использует его неизменённое содержимое; переданный снимок уже не создаёт новый импорт. Конфликт ID отклоняется. При неопределённом fsync или ошибке доставки после commit требуется restart. Гарантия сохранённого учёта не означает exactly-once сторонних обработчиков уведомлений.

Офлайн-пример на Windows:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests_v2 -v
.\.venv\Scripts\python.exe -m mypy
.\.venv\Scripts\python.exe examples\v2_quik_inventory_adoption.py
```

Пример имитирует сбой между журналами. После restart остаток +1 по стоимости 95 получает брокерские связи; исторический fill по 100 с комиссией 1.25 не учитывается заново. Новое исполнение +1 по 100 даёт среднюю стоимость 97.5 и списывает только новую комиссию 0.75. Второй restart сохраняет результат. Все данные синтетические, журналы временные, QUIK не нужен.
