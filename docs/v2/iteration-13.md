# Итерация 13 — защита существующих позиций и завершение офлайн-части этапа 6

Дата: 13 октября 2026 года.

Одиночные входы и уже открытые позиции теперь используют тот же процесс SL/TP/trailing, отмены, ограниченного выхода и восстановления, что многоногий TradePlan. Ручной владелец может подключить защиту после сверки внешнего остатка. Финансовый учёт остаётся в прежнем ledger; подключение не создаёт сделку, комиссию или входную заявку.

## Два способа подключения

| Ситуация | API и поведение |
| --- | --- |
| Новый одиночный вход | `TradePlan` принимает одну или несколько различных ног. `context.place_plan(...)` сразу задаёт политику защиты будущих исполнений. При частичном входе защищено только фактически исполненное; выход ждёт отмены остатка и поздних fills. |
| Позиции уже открыты | `ProtectPositions(operation_id, expected_revision, strategy_id, marks, protection, exit_prices, order_timeout=30)` подключает одну группу ко всем открытым позициям владельца. Идентификатор берётся из `marks.plan_id`. |
| Действие оператора | `runtime.protect_positions(command)` допускает в том числе manual и приостановленную загруженную стратегию. Обычная стратегия должна объявить инструменты группы. |
| Действие стратегии | `context.protect_positions(command)` доступно RUNNING-стратегии для собственного владельца и объявленных инструментов. |
| Дальнейшее управление | Прежние `mark_plan`, `update_plan_protection`, `close_plan`, `retry_plan`, `acknowledge_plan` и `check_plan_deadlines`. |

Для подключения нужны ненулевые позиции, готовность OMS, отсутствие активного плана, аварийной блокировки, незавершённых заявок и барьеров отмены владельца. Полные пакеты marks и лимитов должны точно покрывать маршруты позиций. Проверяются временная актуальность, известные исполнения и границы сверки inventory. Ограниченные выходы проходят предварительный допуск по капиталу. Пустые, конфликтующие или запоздалые команды отклоняются атомарно.

При успешном подключении состояние сразу OPEN и немедленно оценивается по переданным marks. Если порог уже достигнут, в том же переходе фиксируются причина, pause и выход. Приём защиты не гарантирует последующее исполнение лимитного выхода.

## Финансовая база и максимум

`PlanSnapshot.opening_positions` сохраняет фактические количества и среднюю себестоимость при подключении. `opening_pnl` содержит реализованный результат и комиссии текущего незавершённого цикла владельца, полученные через `ledger.open_cycle_pnl`. Результаты завершённых циклов не включаются.

Дальнейший защитный P&L складывается из этой базы, переоценки остатка, денежных потоков и комиссий последующих выходов. Ранее исполненные входы не воспроизводятся. Для импортированного остатка применяется принятая себестоимость; неизвестные комиссии и доходы до начала системного учёта не придумываются. При передаче себестоимость следует за количеством, а уже учтённые комиссии и P&L остаются у прежнего владельца.

Начальная база наследует числовое представление существующего ledger. Сравнения защитных порогов и максимум последующих оценок используют Fraction, как в итерации 12; это не миграция всей бухгалтерии на Decimal.

Максимум начинается с первой принятой оценки. Он сохраняется при изменении параметров, сокращении дефицита и restart. Новая группа после явного снятия получает новый максимум, сохраняя финансовую историю владельца. Переподключением нельзя отменить уже сработавший выход.

## Передача и частичное закрытие manual

`ReleasePositionProtection(operation_id, expected_revision, strategy_id, plan_id)` — явная операторская команда снятия подключённой защиты. Доступна только для OPEN без запроса закрытия, срабатывания, активных заявок, незавершённой аварии и с актуальными marks. Для обычного плана, который сам открывал позиции, она запрещена.

Состояние RELEASED терминально для контроллера защиты, но не означает flat позиции. Старый контроллер больше не принимает marks и не участвует в сокращении дефицита; его история сохраняется. Идентификатор повторно не используется. Комиссии, сделки и владение при снятии не меняются.

Последовательность частичной передачи: приостановить затронутые обычные стратегии → снять подключённую защиту → передать количество через `TransferPosition` → обновить капитал → подключить нужную защиту новым идентификатором. После снятия до нового подключения локальная защита отсутствует; передача сама не переносит SL/TP/trailing. Это явная последовательность отдельных ревизий, а не атомарное изменение всех владельцев вместе с защитой.

При активной защите `CloseManual`, передача и импорт новых manual-остатков/заявок отклоняются. Полное закрытие выполняется через `ClosePlan`; для частичного обычного закрытия требуется предварительное явное снятие. Сверка уже известных остатков и заявок остаётся доступной, в том числе после restart. Ручной ввод новых позиций по-прежнему запрещён.

Защита одного владельца агрегирует P&L всех включённых маршрутов. При внешнем дефиците многоногая обычная стратегия сохраняет соотношение ног. Независимые manual-позиции сокращаются отдельно, начиная с наибольшего количества лотов: общая защита не объявляет для них пропорцию корзины.

## Восстановление и проверки

Новые команды входят в закрытый JSON-словарь. Снимки базовых позиций, P&L, максимума и RELEASED восстанавливаются из последовательности команд. Формат прежних команд не изменён. При restart новый выход ждёт сверки и обновления капитала; прошлые заявки и события повторно не отправляются. CAS, одинаковые повторы и конфликтующие operation_id обрабатываются прежней транзакцией OMS.

Добавлен 21 поведенческий тест; первые 10 написаны до реализации. Проверены long/short и manual, комиссии и частичная реализация, исключение старых циклов, одиночный частичный вход, cancel/late fill, конкурирующие подключения, валидация/codec, частичная передача, независимые manual-позиции при дефиците, сохранение trailing, сбой записи, два replay и API runtime/стратегии. Старый тест минимального количества ног обновлён: пустой план недопустим, одна нога теперь допустима.

Полный набор: **364 теста**, strict mypy — **39 файлов**, **13 демонстраций**. `python examples/v2_position_protection.py` импортирует 4 лота, передаёт 1, защищает оставшиеся 3 и выполняет два перезапуска. Максимум manual 30 RUB, trailing срабатывает при 24; результат manual после комиссии 23 RUB, получателя — 5 RUB, общая закрытая эквити — 28 RUB. Созданы ровно две выходные заявки, фиктивных входов нет.
