# Итерация 4: lifecycle, состояние и оптимизация стратегии

Дата: 9 октября 2026 года, МСК. Следующий срез этапа 3 и первый контракт исторического запроса для UC28. Работа ведётся через XP/TDD; полный market-data/backtest движок остаётся следующим этапом.

## История пользователя

Автор стратегии может сохранить параметры и собственное вычислительное состояние, поставить стратегию на паузу и запустить её функцию оптимизации. Во время расчёта стратегия не получает свечи и не создаёт новые торговые решения. Учёт существующих заявок/исполнений и другие стратегии продолжают работать. По успешному завершению новые параметры сохраняются, затем снимается `OPTIMIZING`.

## Состояния и переходы

| Состояние | Свечи и place/replace | Исполнения, order callbacks и cancel |
| --- | --- | --- |
| RUNNING | Разрешены при готовом хранилище и завершённой сверке | Продолжаются |
| PAUSED | Заблокированы | Продолжаются |
| OPTIMIZING | Заблокированы | Продолжаются |
| FAILED | Заблокированы до явного восстановления оператором | Финансовый учёт продолжается; cancel доступен |

`pause_strategy` / `resume_strategy` — команды оператора вне callbacks. Пауза не отменяет существующие заявки. Возобновление проверяет готовность хранилища и сверку; действующую оптимизацию нельзя завершить командой resume. Пауза во время расчёта сохраняет `OPTIMIZING`, но меняет состояние после его окончания на `PAUSED`.

`context.start_optimization(request, worker)` запускается самой стратегией, в том числе из `on_candle`, и сразу возвращает handle. Ждать `handle.wait()` можно из внешнего управляющего кода; ожидание в callback отклоняется, чтобы очередь стратегии продолжала обслуживать fills. Пример запуска раз в пятницу остаётся логикой стратегии, а не жёстким расписанием платформы.

## Расчёт и данные

Один `HistoryRequest` задаёт инструменты, таймфрейм и UTC-границы. Источник вызывается один раз на расчёт и возвращает tuple завершённых свечей. Свечи вне диапазона, другого инструмента/таймфрейма, дубликаты и запрос будущего отклоняются. `InMemoryHistory` — управляемый источник для проверки контракта; подключения к брокерской истории ещё нет.

Module-level функция получает `OptimizationInput`: историю, копию параметров и копию вычислительного состояния. Она возвращает JSON-объект новых параметров. По умолчанию функция выполняется в отдельном процессе со способом запуска `spawn`; число одновременных CPU-workers ограничено, по умолчанию одним. Core, context, ledger и шлюзы не передаются аргументами worker. Это изоляция выполнения доверенного кода стратегии, а не ОС-песочница.

Результат применяется через `apply_parameters` под блокировкой этой стратегии. Состояние из старого worker-input не переносится поверх актуального состояния: fills, пришедшие за время расчёта, сохраняются. Параметры и текущий checkpoint записываются до разрешения новых решений. Ошибка истории, worker или записи переводит стратегию в `FAILED`; автоматического resume нет.

Результат/отмена относятся к конкретной задаче. Поздняя отмена старого расчёта не меняет статус нового. При обычной остановке runtime ожидает очистку всех созданных задач, в том числе уже заменённых, и завершает собственный работающий процесс. Незавершённый расчёт оставляет паузу.

## Сохранение и восстановление

В общем каноническом журнале появляются отдельные записи `kind: strategy`, версия 1. Сохраняются имя и Python-тип стратегии, версия состояния, инструменты, параметры, вычислительный JSON, статус и причина. Старые OMS-записи читаются без изменения их формата. Неизвестные схемы и некорректные checkpoints отклоняются; финансовые записи не удаляются и не заменяются состоянием стратегии.

`save_state` / `restore_state` — явный контракт автора, без автоматической сериализации Python-объекта. Принимаются JSON-объекты с конечными числами; живые объекты, циклы и NaN/Infinity отклоняются. `state_version` проверяется вместе с Python-типом и инструментами; несовместимое состояние требует отдельной миграции. Getter параметров и worker-input возвращают копии.

Checkpoint сохраняется при регистрации, после callbacks и при переходах lifecycle; доступен и явный `checkpoint_strategy`. После перезапуска автор передаёт экземпляр того же класса: параметры и состояние восстанавливаются, вызывается `on_restore` с отключённой торговлей. `on_start` повторно не вызывается при наличии сохранённого checkpoint. Затем восстанавливается прежний `RUNNING`, `PAUSED` или `FAILED`, с независимым барьером broker reconciliation. Прерванный `OPTIMIZING` восстанавливается как `PAUSED`; задача сама не перезапускается.

При ошибке вычислительного checkpoint стратегия блокируется; для фиксации отказа используется последняя корректная копия состояния, если новая не сериализуется. Канонический финансовый учёт остаётся владельцем позиций/сделок/эквити. Callback и его финансовые последствия не становятся одной транзакцией со стратегийным checkpoint: восстановление не переигрывает старые callbacks.

## Приёмка

Всего **104 теста**, из них **21 новый** для lifecycle/оптимизации; один прежний тест сравнивает неизменность журнала при конфликте вместо фиксированного числа OMS-записей. Проверяются pause/resume, единственный массовый запрос, работа соседней стратегии и fills во время расчёта, сохранение параметров/состояния и финансовой истории, несовместимая версия, невалидные данные, отказ worker, late cancellation и очистка заменённых задач.

Два сценария используют настоящие дочерние процессы: вычисление подтверждается другим PID; ещё работающий CPU-worker завершается при shutdown. Отдельный аварийно завершающийся процесс сохраняет `OPTIMIZING`, а новый runtime восстанавливает паузу. Strict mypy и четыре демонстрации включены в CI Linux/Windows.

`examples/v2_optimization.py` запускает расчёт из стратегии: её счётчик остаётся на одном баре, соседняя получает два, один исторический запрос даёт period 3. Fill обрабатывается во время `OPTIMIZING`. После рестарта восстанавливаются period 3 и счётчик fill; после сверки выход закрывает цикл с эквити 18 RUB.

## Границы следующего среза

Есть только поддерживаемые сейчас candle callbacks. Тики/стакан, календарь, synthetic/correction, историческое исполнение и одиночный бэктест ещё впереди. Пропущенные во время паузы бары автоматически не воспроизводятся; прогрев/обновление индикаторов будет связан с контрактом market data. Автор может пересоздать производные объекты в `apply_parameters` / `on_restore`, а совместимое долговременное состояние определяет через свои hooks.

`stop`, flatten/emergency exit, загрузка `.py`, обновление кода с передачей позиций, GUI/Telegram, реальная защита SL/TP и QUIK не считаются реализованными этим срезом. Хранилище и сериализация всё ещё синхронны в ядре; нагрузочная изоляция ввода/вывода остаётся до production. Worker и состояние не загружаются по строке из журнала: экземпляр класса и функцию передаёт доверенный управляющий код.
