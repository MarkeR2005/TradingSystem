# Итерация 18 — точная идентификация фьючерсных лимитов

17 октября 2026 года. Пятый срез этапа 7, ветка `rewrite/v2-quik-limits` поверх `rewrite/v2-quik-parameters`.

В пользовательском демо-наблюдении есть четыре строки лимитов одного счёта. Их типы и валюты различаются, поэтому автоматическое суммирование или выбор первой строки могли бы исказить капитал. Новый срез сохраняет перечень строк, проверяет принадлежность счёту и позволяет явно проверить одну выбранную строку. [Инструкция запуска](quik-limits-check.md) вынесена отдельно.

## Контракт выбора

`FuturesLimitKey` содержит точные `firmid`, `trdaccid`, `limit_type`, `currcode`. Для двух первых полей действует прежний контракт идентификатора маршрута; тип — целое число, исключающее bool. Пустая валюта допустима как наблюдаемая идентичность. Преобразование SUR/RUB в RUB для отображения валютного смысла не меняет ключ.

`build_limits_report` проверяет два набора таблиц `getTradeAccounts` и `getFuturesClientLimits`. Фирма/счёт должны однозначно соответствовать строке торговых счетов, а `class_codes` — содержать отдельный токен SPBFUT. Дубликат полного ключа отклоняется даже при одинаковых суммах. Неизвестные типы сохраняются с диагностикой. Неполная таблица, неверный счёт или некорректная любая строка не дают подтверждённого выбора.

Без `selection` работает инвентаризация: полная повторяемая выборка допустима, но `selection_verified=False`. При явном выборе поддерживается только тип 0 с точным кодом SUR или RUB. Выбор считается подтверждённым лишь при единственном совпадении в обоих проходах и отсутствии диагностических причин отказа. Типы 3/6/7 остаются в перечне; их суммы не добавляются к типу 0, отрицательные значения не запускают сокращение позиций.

## Поля и единицы

Основание для названий и типов — официальное **«Руководство пользователя Интерпретатора языка Lua», версия 13.2 (2026), раздел 4.9**, из [архива ARQA Technologies](https://arqatech.com/upload/iblock/114/quik_lua.zip). Для сопоставления ключа нужна таблица «Ограничения по клиентским счетам»; полный ключ также указан в [ответе поддержки QUIK](https://forum.quik.ru/forum10/topic2942/).

| Поля | Как используются в этом срезе |
| --- | --- |
| `cbplimit` | Наблюдаемый лимит открытых позиций. Не объявляется equity счёта. |
| `cbplused`, `cbplplanned` | Текущая и плановая оценки чистых позиций. Из них не выводится формула свободного капитала. |
| `cbplused_for_orders`, `cbplused_for_positions` | Отдельные наблюдения ресурса под заявки и под уже открытые позиции. |
| `varmargin`, `real_varmargin` | Расчётная и фактически начисленная при клиринге вариационная маржа. Хранятся раздельно. |
| `kgo` | Коэффициент клиентского ГО, а не денежная сумма. |
| `cbp_prev_limit` | Предыдущее значение лимита; не заменяет текущее. |
| `go_without_orders`, `go_planned` | Две оценки ГО без заявок с различными риск-параметрами. Не подменяют BUYDEPO/SELLDEPO инструмента. |
| `liquidity_coef`, `accruedint`, `options_premium`, `ts_comission`, `indicative_varmargin`, `net_option_value` | Дополнительные наблюдения; не складываются автоматически в баланс. |
| `risk_level` | Целый код 0–4; не преобразуется в плечо или торговый допуск. |

Первые четыре строки таблицы и `kgo` обязательны для полноты диагностической строки. Остальные поля могут отсутствовать: сохраняется `null`. Некорректное присутствующее поле делает наблюдение неподтверждённым. Машинные числа преобразуются через Decimal в десятичные строки без дополнительного округления; исходную точность JSON-числа сверх полученной записи восстановить нельзя. Записи с разделителями, NaN/Infinity и bool отвергаются. Длина числовой строки ограничена 80 символами. Нули и отрицательные значения сохраняются как наблюдения; положительность, требуемая для финансового кандидата инструмента, сюда не переносится.

В этом срезе нет подтверждённого правила преобразования этих полей в `AccountCapital`, `CapitalSnapshot` или `CapitalPolicy`. В частности, `cbplplanned` не переименовывается в available capital. Признаки `eligible_for_capital`, `eligible_for_trading`, `reconciled` всегда false.

## Снимок, CLI и файлы

`capture_snapshot(..., include_limits=True, limit_selection=...)` повторно использует прежние два чтения таблиц. Сравниваются исходные записи без зависимости от порядка строк; изменения любого поля сохраняют признак нестабильности. Изменение других таблиц, даты, callbacks или ошибка финансовых параметров тоже блокируют выбор. В совместном режиме ошибка лимитов снимает `point_value_candidate` и подтверждение финансового наблюдения. Два прохода не становятся атомарной границей брокерского состояния.

Новых команд протокола, Lua-capability, подписок, retry и сетевых разрешений нет. Опция `--limits` добровольная; прежний запуск остаётся совместим. Полный ключ CLI проверяется до создания файлов и открытия соединения. Выходы 0/2/1 сохраняют прежний смысл успешного наблюдения / неподтверждённого чтения / ошибки; неправильные аргументы отклоняет argparse с кодом 2.

`limits.json` содержит нормализованные поля обоих проходов и выбранной строки с одинаковыми условными именами счетов. В нём нет исходных таблиц счетов, ордеров, сделок или произвольных полей терминала. `limit-keys.local.json` отдельно сохраняет полные наблюдённые ключи для локального сопоставления. Условные имена не предназначены для постоянной конфигурации, денежные суммы в `limits.json` сохраняются. Существующие `report.json` и wire-журнал остаются локальным аудитом с полными данными. Все файлы записываются в UTF-8 исключительно в новый каталог.

## Проверки и границы

Добавлены **38 тестов**, всего **521**. Локально прошли полный набор, strict mypy по **52 файлам** и **18 примеров**. CI выполняет те же проверки на Linux и Windows; итог фиксируется в draft PR.

TDD покрывает точный ключ, независимость SUR/RUB, дубли, счёт/класс, типы и отсутствующие поля, знаковые суммы, изменение любого прохода и влияние остального снимка. TCP-стенд проверяет совместимость старого режима, отсутствие новых команд, взаимное снятие подтверждения финансовых параметров и лимитов, экспорт с условными именами и ошибки CLI до побочных действий. Отдельный пример использует вымышленные реквизиты и суммы.

Ранее приложенный пользователем снимок локально проверен новым анализатором: сохранены четыре строки, точный выбор строки типа 0 проходит, экспорт не содержит идентификаторов фирмы/счёта. Это проверка совместимости с уже сохранёнными данными, не новое подключение к терминалу. Исходные реквизиты и суммы в код, тесты и документацию не перенесены.

Получены `status=captured`, `limits.empty`, неподтверждённое наблюдение и отсутствие допуска капитала. Это согласуется с выходным режимом официального демо.
