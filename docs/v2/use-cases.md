# Согласованный реестр use-case

Дата: 8 октября 2026 года. Статус: **согласован пользователем**, ответы Q1–Q4 учтены. Основание: договорённости по TradingSystem, [архитектурный эскиз](architecture.md), [план](development-plan.md) и код двух первых итераций v2.

## Что считаем

Один use-case — одна самостоятельная цель автора стратегии, оператора или исследователя либо функциональный результат обработки внешнего события: восстановиться после сбоя, устранить дефицит и т. п. Нормальный ход, отказ, повтор и перестановка сообщений — ветви этого сценария. Число классов, типов событий, этапов разработки и тестов не определяет число use-case.

Реестр содержит **32 use-case в 8 группах**. Нумерация согласована; ответы Q1–Q4 не добавляют новых сценариев. Портфельный бэктест (UC25) реализуется отдельной итерацией после одиночного, дополнительные шлюзы (UC32) — после QUIK. UC28 означает оптимизацию внутри стратегии, без обязательного общего сервиса параллельного перебора в первой версии. Варианты поведения уточняются acceptance-сценариями.

137 существующих тестов проверяют отдельные ветви нескольких сценариев. Они не означают, что готово 137 пользовательских сценариев. Исходный прототип `core/` / `gui/` не считается реализацией новых use-case v2.

## Правила внутри сценариев

Эти правила не прибавляют отдельные use-case, но каждое должно иметь приёмочные проверки.

1. `desired_leverage` — модификатор веса: произведения весов и модификаторов нормируются к общей сумме. Максимальное плечо задаётся на счёт. Ручная стратегия имеет вес 0, но её позиции занимают ёмкость.
2. Распределение учитывает доступные счета, пропорции ног, резервы и занятые ресурсы; остатки перераспределяются итеративно.
3. Позиции и финансовый результат принадлежат стратегии виртуально; противоположные позиции двух стратегий не сливаются в их учёте. Внутреннее crossing между стратегиями не входит в начальную версию.
4. Только исполнения меняют позицию. Отправка, ack и отмена не являются сделкой. Перенос владения также не должен создавать фиктивный рыночный fill.
5. Закрытая эквити меняется после flat всех ног. Комиссии, средняя стоимость, переворот, дубликаты и валютное приведение учитываются явно.
6. Cancel/replace: подтверждение окончательной отмены плюс учёт всех предшествующих fills; затем новая заявка на остаток. Отсутствующий ответ не означает успешную отмену. Production default ожидания ack/cancel — 90 секунд.
7. Защита ставится сразу на исполненное количество. Для общей защиты корзины используется её совокупный P&L. Iceberg относится к исполнению ордера, trailing — к защите/логике выхода.
8. При внешнем дефиците сохраняется соотношение ног; восстанавливается только дефицит. Незавершённый вход корзины и внешний дефицит — разные ситуации.
9. Исторические события с одним временем: order/fill, candle, timer. Новая заявка не исполняется уже полученным баром. Лимит исполняется по действующей лимитной цене; стоп не исполняется на баре активации. Частые перестановки и Монте-Карло отдельно от первоначальной модели.
10. Синтетика: live использует last, при отсутствии допустим mid; история — предыдущий close. Без начальной цены ошибка. Коррекция имеет отдельную семантику.
11. Финансовая история сохраняется при обновлении стратегии и сбросе вычислений. Канонические исполнения/сделки, read models и reconcile не подменяют друг друга.
12. GUI, удалённое подтверждение и исследования не владеют live-объектами ядра. Исследование получает собственную копию конфигурации/состояния. Тяжёлые вычисления требуют изоляции; это ограничение архитектуры, а не дополнительный use-case.

Самостоятельная мобильная программа, web/VPS-развёртывание, визуальный конструктор стратегий и отдельная инфраструктура обучения ML не включены в этот реестр как согласованные цели первой версии. Возможность использовать модель/индикатор в `.py` относится к UC01/UC06. Идеи из README прототипа не превращаются автоматически в требования v2.

## Границы команд и решения Q1–Q4

**pause** прекращает торговую логику и новые решения, сохраняя обработку заявок/исполнений и защиту; сама по себе заявки не снимает. **stop** отменяет активные заявки и ждёт исходов; закрытие позиций определяется отдельной shutdown policy. **cancel_orders**, **flatten**, **emergency_cancel**, **emergency_exit** различаются по результату.

| Решение | Согласованное поведение |
| --- | --- |
| Q1 / UC08 | Ручного ввода новых заявок из GUI нет. Ручная стратегия принимает переданные и внешние позиции/заявки; её позиции можно закрывать или передавать другим стратегиям целиком и частями. Передача фиксирует владение, сохраняет финансовую историю и не создаёт фиктивных fills. |
| Q2 / UC06, UC11, UC23 | Многоногая стратегия явно декларирует политику отказа/зависания ноги: защита исполненного, достроение или закрытие. Выбранное аварийное действие выполняется при pause и alert; обычные решения приостановлены. Это отдельная политика от сокращения внешнего дефицита. |
| Q3 / UC25 | Портфельный бэктест допускается следующей отдельной итерацией после базового одиночного. Общие контракты ядра сохраняют возможность такого расширения. |
| Q4 / UC28 | Оптимизация принадлежит стратегии. `OPTIMIZING` блокирует доставку рыночных событий и новые торговые решения этой стратегии. Явный массовый запрос истории доступен для расчёта. По успешному завершению оптимизации статус снимается; исполнение существующих заявок, их учёт и защита продолжаются. Ошибка расчёта не должна автоматически возобновлять торговлю. |

Еженедельный запуск и расчёт продолжительностью около часа — пример политики стратегии, а не обязательное расписание платформы. Тяжёлый расчёт должен выполняться отдельно от торгового event loop. Политика отмены существующих входных заявок, повторного прогрева и обновления данных после оптимизации будет уточняться при реализации lifecycle; переход в статус сам по себе не отменяет защиту.

Согласованный реестр не означает готовность всех 32 сценариев. Текущие границы и результаты остаются в отчётах об итерациях; новые ID добавляются без переименования старых.
