# Итерация 22 — применение сохранённых исполнений QUIK

21 октября 2026 года. Ветка `rewrite/v2-quik-repair` от `rewrite/v2-quik-compare`. Этап 7 продолжается; реестр сохраняет 32 use-case.

## Результат

OMS может одной журналируемой операцией учесть исполнения, которые уже сохранены durable-шлюзом, присутствуют в проверенном брокерском наблюдении, но отсутствуют в OMS. Повтор этой операции сохраняет позицию и комиссию без повторного учёта. После применения торговля остаётся заблокированной, а прежняя политика капитала требует обновления.

Это ограниченное исправление доставки положительного факта исполнения. Оно не завершает независимую сверку брокера: атомарность снимка, полнота истории, внешние позиции, неизвестные исходы отмен и граница возобновления остаются отдельными задачами. `ComparisonReport.can_apply`, `reconciled` и признаки торгового допуска по-прежнему равны `False`.

## Какие данные допускаются

`ExecutionEvidence` содержит сохранённые связи брокерских и локальных ID, revision шлюза и точные payloads `Execution` в порядке их фиксации протоколом. Порядок не сортируется по номеру сделки или времени. Digest охватывает payloads, связи, сессию и revision. Это идентификатор аудита внутри доверенного процесса, а не подпись брокера и не средство авторизации недоверенного клиента.

`build_execution_repair` повторно запускает сравнение полного read-only снимка. Требуются известные комиссии и точное совпадение маршрута, локальной заявки, стороны, количества, цены, комиссии и времени с сохранённым исполнением. Внешние/несопоставленные записи, неполное покрытие сделок заявки и остальные расхождения за пределами исполнения приводят к отказу. Различия статуса, связанные с неизвестным исходом заявки/отмены, не разрешаются автоматически.

Разрешён только **недостающий конец сохранённой последовательности**. Если после пропуска OMS уже учёл более позднее исполнение шлюза, дописывать старое исполнение нельзя: порядок влияет на себестоимость и P&L. Уже учтённая часть должна точно совпадать с источником. Пропущенные исполнения не должны предшествовать уже учтённой истории владельца; равное время с другим шлюзом также считается неоднозначным.

Этот срез отклоняет исправления для затронутых активных планов/защиты и маршрутов аварийного сокращения. Также отклоняются истории gateway с inventory cutover и владельцы с передачами позиций: для них нужна отдельная процедура восстановления истории. Терминальная заявка не получает новые fills через этот API.

## Проверка и запись

`RepairExecutions` содержит уникальный ID операции, ожидаемую revision OMS, сессию/revision/digest источника, digest снимка, времена наблюдения/создания/истечения, исполнения, целевые накопленные количества заявок и совокупные нетто-позиции. Срок действия заканчивается через `max_age` от **начала наблюдения**, а не от создания команды.

Применение выполняется через `QuikDurableGateway.apply_execution_repair(command, runtime.orders)`, вне обработчиков шины событий. Прямой `orders.handle(command)` отклоняется. Метод сначала дожидается очереди, затем под блокировками шлюза и OMS проверяет источник, журнал и неизменность revision. Новый repair запрещён при повреждённом/закрытом журнале, смене владельца журнала или состоянии шлюза, требующем перезапуска. Такой отказ не заменяет процедуру restart.

OMS выполняет исполнения на изолированной копии своим обычным финансовым путём. Проверяются конечные накопленные количества/параметры заявок и совокупные позиции всех владельцев. Ошибка любого исполнения или итогового сравнения отбрасывает всю копию и накопленные уведомления. При успехе сначала сохраняется одна команда в журнал, затем принимается новое состояние и публикуются уведомления.

Резерв незаполненной части заявки пересчитывается обычным учётом fill: занятость переходит в позицию. Неизвестная отмена не освобождает резерв; даже достигнутый барьер cancel не запускает замену внутри repair. Операция не создаёт `GatewaySubmit`/`GatewayCancel` и не продвигает планы/аварийные сценарии. Пользовательские обработчики уведомлений сохраняют обычную ответственность стратегии; новые входы/replace блокируются состоянием OMS.

## Повтор и восстановление

Точный повтор ID и содержимого — no-op, в том числе после истечения срока, продвижения шлюза и restart. Другие данные с тем же ID отклоняются. Новая команда с другим ID обязана пройти все проверки заново. Обычная повторная доставка тех же fills шлюзом также не меняет финансовый результат.

Ошибка записи не публикует новое состояние. При неопределённой долговечности журнал блокирует дальнейшие записи до restart. Если запись состоялась, но доставка уведомления прервалась, OMS требует restart; повтор команды в том же процессе не маскирует сбой. Восстановление переигрывает сохранённую команду на исторической revision/времени, затем повторная доставка шлюза дедуплицируется. API не вводит гарантии exactly-once для произвольных внешних эффектов пользовательского `on_fill`.

## API и демонстрация

```python
await runtime.drain()
view = runtime.orders.observe_gateway(gateway.gateway_id)
command = build_execution_repair(
    operation_id, raw_snapshot, comparison_policy, view,
    gateway.execution_evidence,
    now=clock.now(), current_revision=runtime.orders.revision,
)
# Команду можно показать оператору до применения; после задержки она может устареть.
await gateway.apply_execution_repair(command, runtime.orders)
await runtime.drain()
assert not runtime.orders.ready
```

Для офлайн-проверки на Windows:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests_v2 -v
.\.venv\Scripts\python.exe -m mypy
.\.venv\Scripts\python.exe examples\v2_quik_repair.py
```

Пример использует синтетические данные и временные журналы. Сначала намеренно теряет доставку сохранённого исполнения, затем применяет repair: позиция 1 лот, комиссия 1.25 RUB, резерв остатка заявки 450 RUB. Повтор и restart не создают второго fill или новой подготовки транзакции. QUIK для примера не нужен; настройки терминала, локальный профиль и порты не меняются.
